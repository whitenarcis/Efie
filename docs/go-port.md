# Перенос на Go: план и замеры

Зачем. Python-бот — это один процесс, в котором на каждом сообщении
считается эмбеддинг (ONNX-модель ~1 ГБ весов под `threading.Lock`), TF-IDF
индекс копируется под локом, а numpy-матрица корпуса строится заново. Всё это
живёт в одном процессе вместе с ботом, поэтому RAM и CPU страдают одновременно
и лечатся одинаково: тяжёлую память нужно вынести из Python.

Принцип переноса. Не «переписать всё», а по одному подсистеме за раз, и
каждый перенос обязан быть:

1. **доказуемым по паритету** — `internal/parity` гоняет настоящий Python-код
   (`efi.memory.*`, `efi.llm.schemas`) и сравнивает его результат с Go по
   «золотым» значениям в `internal/parity/testdata/goldens.json`. Если
   Python-сторона меняется — золотые значения перегенерируются
   (`PYTHONPATH=src python internal/parity/gen_goldens.py`), иначе тест падает
   и напоминает, что реализации разошлись.
2. **доказуемым по деньгам** — замер RAM/CPU одной командой, на одинаковом
   корпусе и одинаковых запросах, без бота и без сети.

## Где мы сейчас

Перенесено ядро памяти — процесс `cmd/efie-memory`:

| Подсистема | Python | Go |
|---|---|---|
| Дневник (`.md` + sidecar `.vec.json`) | `efi/memory/diary.py` | `internal/diary` |
| TF-IDF фолбэк | `efi/memory/tfidf_fallback.py` | `internal/tfidf` |
| Оркестратор поиска (лестница эмбеддингов, дедуп) | `efi/memory/rag.py` | `internal/memory` |
| HTTP API | — | `internal/memapi` |

Оркестратор бота — Python. Переходный режим: бот ходит в `efie-memory` по
HTTP на localhost, сервис можно перезапускать без остановки бота.

## Замеры

Одинаковые условия с обеих сторон: 5000 записей, размерность векторов 1024,
200 поисковых запросов, тот же генератор корпуса и те же опции запросов
(`max_entry_count=10`, `min_relatedness=0.80`).

Go (генерация и замер в одном процессе, GC отдаёт освобождённое):

    go run ./cmd/efie-memory -bench 5000 -bench-dims 1024 -bench-queries 200

Python (генерация отдельным процессом, замер — в свежем, который только
читает корпус; это эквивалентное условие, потому что Python не возвращает
память ОС):

    python internal/parity/bench_python.py gen /tmp/efie-bench-corpus
    python internal/parity/bench_python.py run /tmp/efie-bench-corpus

Результаты на одинаковом корпусе:

| Метрика | Python | Go | Выигрыш |
|---|---|---|---|
| холодная загрузка корпуса | 3.87 с | 1.04 с | ×3.7 |
| сборка TF-IDF индекса | 0.17 с | 0.06 с | ×2.8 |
| TF-IDF поиск, мс/запрос | 84.0 | 16.8¹ | ×5.0 |
| векторный поиск, мс/запрос | 176.4 | 13.2 | ×13.4 |
| RSS после загрузки + индекса, МБ | 341.7 | 109.3 | ×3.1 |
| RSS итого после 200+200 поисков, МБ | 480.0 | 124.2 | ×3.9 |
| прирост RSS на корпус, КБ/запись | 89.4 | 23.5 | ×3.8 |

¹ Go-число — полный путь `Search` (проверка короткого сообщения, попытка
эмбеддинга, TF-IDF-фолбэк, дедупликация): оно включает в себя то, что в
Python считается отдельно.

Это только ядро без самого тяжёлого: локального embedding-движка
(fastembed + onnxruntime + веса e5 ~1 ГБ), который в Python живёт в том же
процессе, что и бот. В Go его место — `-embedder=local-onnx`
(`internal/embed`), следующий шаг переноса.

## Следующие шаги

1. **`local-onnx`** — инференс multilingual-e5 прямо в Go
   (onnxruntime_go + токенизатор), тот же уровень лестницы, что и fastembed
   в Python. Место в `buildLadder` уже готово (`cmd/efie-memory/main.go`),
   пакеты `internal/embed` и лестница менять не потребуют.
2. **Клиент в Python** — заменить прямые вызовы `efi.memory.*` на HTTP-клиент
   `efie-memory`, сохранив контракт (опции, фильтры по доменам, исходный
   уровень поиска в ответе).
3. **Консолидация и запись** — перенос `remember`, ночной консолидации и
   prune, чтобы дневником владел только Go-процесс.
